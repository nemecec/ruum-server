# Backlog 2026-11-24 (card D-5: the app role kinds of a binding)

the integrator may renumber them. Kinds, efforts and handlings are as in
`docs/backlog/2026-11-08.md`. All decisions here are `provisional` (design 18.9).

| D5-1 | gap | Credential renewal for a long-running app. `RUUM_BINDING_<NAME>` is read at start, and the password has `VALID UNTIL` (default 1 h, at most 24 h). Either the runtime restarts instances before expiry, or the runtime API gets an additive "fresh database credentials" path. | card D-5 "Open questions"; `AppRoles::issue_credentials` | M | **panel**, then B-1d: choose the delivery. | D5-2 | gap | SQLite databases cannot be bound: an app cannot reach a SQLite file (DESIGN 14 lists SQLite as an engine). `AppRoles::ensure_binding_role` refuses a SQLite database with `422 validation_failed` until a design exists. | card D-5 "Open questions" | S | **panel**: a design (a read replica file? a proxy?) or a permanent refusal; B-1d keeps the refusal. |
| D5-3 | gap | `temp_file_limit` of an app role is set only when `ruum_dbhost` holds `SET` on the parameter; the cluster set-up does not grant it yet, so the engine warns once and the app has no temp file limit (the cluster default, unlimited). | `postgres/app_roles.rs` `settings_sql`; test `temp_file_limit_is_set_and_the_app_cannot_raise_it` grants it as the superuser | S | **I-x (deploy)**: `GRANT SET ON PARAMETER temp_file_limit TO ruum_dbhost` in `deploy/dev/postgres-data/initdb/10-ruum-data.sh` and on staging; then the engine sets it on every new password. |
| D5-4 | gap | The pooler (STEP3 rule 2, the network half). App roles reach the cluster only from the platform address today (the laptop `pg_hba.conf` lets every `r_` role in from there); sandbox networks reach nothing until I-4 adds one pooler with `pg_hba` lines per database and role. The pooler must authenticate the short-lived SCRAM passwords: PgBouncer `auth_query` (a function that reads `pg_authid` as a superuser-owned SECURITY DEFINER role) or SCRAM passthrough. What the engine exposes: the role name, the database name and the password (`AppCredentials`); the verifier is in `pg_authid` (the engine sends only the verifier). `AppCredentials.host`/`port` are the engine's address and must become the pooler's. | card D-5 "Open questions"; STEP3 "How an app runs" rule 2 | M | **I-4** (laptop), a staging card: the pooler, its `pg_hba` lines, and a setting of the engine for the address it hands out. |
| D5-5 | gap | `pg_database` and `pg_roles` are readable cluster-wide by any login role, an app role too. The names are neutral (`d_`/`r_` + random hex), so an app learns only how many databases and roles the cluster has (and the connection limits of app roles). | card D-5 "Open questions" | S | **accepted residual** for step 3; hardening option: a cluster per tenant tier, or a pooler that answers catalog queries. |
| D5-6 | gap | Role settings `statement_timeout` and `idle_in_transaction_session_timeout` of an app role are defaults: the app may change them in its session, and `ALTER ROLE <itself> SET` of a user setting lasts until the next `issue_credentials` (which resets every setting). Only `temp_file_limit` (D5-3) and the connection limit are hard. | `postgres/app_roles.rs` module doc | S | **accepted** (an app's own load); a hard limit needs the pooler (D5-4: `query_timeout`, `idle_transaction_timeout`). |
| D5-7 | gap | A copy fails (`objects of the copy still depend on the source's roles`) when a policy of the source names a role of step 2 (`TO <the write kind>`): the hand-over strips the policies of foreign roles (app roles) but does not map a policy's step 2 roles to the copy's. Only a migration that names an engine role (it can read the names in `pg_roles`) makes one. Seen while writing the D-5 copy test. | `postgres/copy.rs` `hand_over`; `app_roles::strip_policies` | S | **next engine card**: map each step 2 role of a policy to the copy's role of the same kind. |
| D5-8 | gap | The per-tenant cap (`MAX_APP_ROLES_PER_TENANT` = 20) counts the platform rows; the cluster budget counts the connection limits of every app role in `pg_roles` (half of `max_connections` by default). A role left by a crash between the engine and the row counts against the budget until `AppRoles::repair_node` runs; B-1d must call the repair (at start and in its binding repair loop). A trashed database does not stop `ensure_binding_role` (B-1d checks the trash). | `databases/app_roles.rs` module doc | S | **B-1d**: call `repair_node`, refuse bindings of a trashed database. |
| D5-9 | gap | The memory `AppRoleStore` is separate from the memory `DatabaseStore`, so a purge on the in-memory services leaves app rows (the Postgres purge deletes them with every `database_roles` row).
