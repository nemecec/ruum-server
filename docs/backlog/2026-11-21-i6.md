# Backlog 2026-11-21, card I-6 (the app runtime on staging)

Items left by card I-6 (`ops/i-6`): gVisor on the staging Talos nodes, the app gateway and the
egress proxy deployed by the charts, their network policies, the apps domain on the edge and the
smoke checks (`deploy/staging/README.md` "The app runtime"). The IDs are `I6-n` so that they do
not collide with the run backlogs. Kinds, efforts (S, M, L) and handlings are as in
`docs/backlog/2026-11-08.md`. All decisions here are `provisional` (design 18.9).

| I6-1 | gap | **No runtime driver starts sandboxes on Kubernetes.** The Docker driver (`crates/ruum-runtime`, R-2a) needs a Docker engine; Talos has none. `ruum-server` keeps the in-memory driver and no `SandboxDirectory` (`wiring.rs`), so the internal `upstream` route answers `not_running` and every node22 request ends in the gateway's 502 after the sign-in. | I6-2 | question | **The egress proxy's identity on Kubernetes.** The proxy knows an app by a registered subnet and takes registrations on a control socket that must be on no network it serves (Unix socket or loopback). Pods share the node's pod range, so a Kubernetes driver must register each pod address (`/32`), and reach the control listener: (a) the proxy as a sidecar of `ruum-server` (the socket on a shared emptyDir; sandboxes then reach the server pod's 3128 only), (b) a TCP control listener with mutual TLS or the token on a separate pod network address (an `ruum-egress` change: today it refuses a non-loopback control address), or (c) the driver runs in the proxy's pod. Also: a proxy restart forgets every registration; the driver must register again (README "Control listener"). | `crates/ruum-egress/README.md` "Control listener"; `charts/ruum/templates/egress.yaml` | M | **panel**, with I6-1. |
