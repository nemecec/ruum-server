# Backlog 2026-11-28 (card W-3b: approvals of agents' publishes)

What card W-3b decided provisionally and left open (`ruum-server-wt/panel/impl-w3b.md`). IDs
`W3B-Dn` (provisional decisions, design 18.9) and `W3B-n` (open items); the integrator may
renumber them. Kinds, efforts and handlings are as in `docs/backlog/2026-11-08.md`.

| ID | Kind | Item | Evidence | Effort | Handling |
|---|---|---|---|---|---|
| W3B-D1 | decision (provisional) | The 15 minutes of use count from `decided_at`: an approval moves `expires_at` to `decided_at + 15 min`, and the use also checks `decided_at` itself. A pending request expires `APPROVAL_HOURS` (24 h) after it was made. A pending or approved row past `expires_at` reads as `expired` **on read** (`approvals::status_at`, the list's status filter, the long poll); nothing writes `expired` and there is no sweeper step (as A-2). | `apps/approvals.rs` `status_at`, `check_use`, `decided`; tests `only_an_approved_unused_approval_within_15_minutes_is_used`, `a_pending_request_past_its_time_is_expired` | S | **panel**: confirm. |
| W3B-D2 | decision (provisional) | "The agent that asked" is the same agent ID and the same `on_behalf_of` user (the whole actor pair); any API key of that agent counts. Another agent, the same agent for another user, the user itself, another deployment, app or tenant all get the same `409 approval_stale` as a missing approval, so an agent learns nothing of other requests. `getAppApproval` of another agent's request is `404`. | `check_use`, `AppStore::take_approval`; tests `only_the_agent_that_asked_uses_an_approval_for_its_deployment`, test kit case `an_approval_is_only_for_the_agent_that_asked` | S | **panel**: confirm. |
| W3B-D3 | decision (provisional) | The approval is taken (`used`, `used_at`) **before** the release, in one store statement that checks approved, unused, the window, the actor pair, the app and the deployment again (two publishes with one approval: exactly one gets it). It is not taken in the release transaction, because card W-3a-m runs the migrations between the take and the release and needs the approval taken by then. A release that fails after the take leaves the approval used; the agent asks again. The release records the approval (`DeploymentRow.approval_id`, `app.deployed.approval_id`). | `AppService::publish_approved`; tests `a_failed_release_leaves_the_approval_used`, `two_publishes_with_one_approval_make_one_release` | S | **panel**: confirm (or take it under the live switch once W-3a-m knows its order). |
| W3B-D4 | decision (provisional) | A repeat request of the same agent pair for the same deployment while its request is pending and the archive hash, manifest hash, binding targets and `changes` still match returns that request (`202`, no new row). At most 50 pending (not expired) requests per app; past that `409 conflict`. Requests of one app are serialized (an advisory lock on Postgres). | `AppStore::request_app_approval`; test `a_repeated_request_returns_the_pending_one_and_an_app_holds_at_most_50` | S | **panel**: confirm the number. |
| W3B-D5 | decision (provisional) | A person's publish **ignores** `approval_id` (it runs with the person's own checks and never looks the approval up), rather than refusing it. | `deployments.rs` `publish_deployment`; test `a_persons_publish_ignores_approval_id` | S | **panel**: confirm. |
| W3B-D6 | decision (provisional) | A deny takes no `telemetry_fields` and no `classes` (`422`). A class must name a planned column of the request (`422`, pointer `/classes/<i>`; a column named twice too), unlike `DecideDatabaseApprovalRequest.classes`, where an unknown column is ignored. `telemetry_fields` are confirmed before the decision is stored; a confirmation that succeeds and a decision that then loses a race (another decision came first, `409`) leaves the fields confirmed (a person with `manage` confirmed them). | `decide_approval`; tests `who_decides_and_with_which_rights`, `a_refused_telemetry_confirmation_leaves_the_request_pending` | S | **panel**: confirm. |
| W3B-D7 | decision (provisional) | The use compares only the parts of `changes` that say what the publish does (`bindings_added`, `bindings_removed`, `roles_added`, `roles_removed`, `secrets_missing`, `migrations`, `planned_columns`), not the counts of unconfirmed fields, which change when telemetry comes in. A live deployment that changed since the request is stale only when the changes differ. | `approvals.rs` `CHANGE_KEYS`; test `every_stale_approval_is_refused_and_nothing_goes_live` | S | **panel**: confirm (or also bind the live deployment ID, which needs a column). |
| W3B-1 | gap | `changes.unconfirmed_telemetry_fields` stays 0: the request runs inside `AppService`, which has no handle on the telemetry field store, and the wiring that would give it one is in `telemetry::query::install` and `crates/ruum-server` (not this card's files). | `AppService::requested` | S | **O-2 owner or W-1 owner**: a field-count handle on `AppService` (as `set_privacy_suggestions`), set where the telemetry service is installed. |
