# Backlog 2026-11-12 (product ideas of the person: app sharing and billing)

From the person's ideas and comments on 2026-11-12, written into the design as sections 9.13 and
21.7 (decisions 43 and 44, both provisional). Kinds, efforts and handlings are as in
`docs/backlog/2026-11-08.md`. All decisions here are `provisional` (design 18.9).

## 1. Sharing apps between tenants (design 9.13)

| ID | Kind | Item | Evidence | Effort | Handling |
|---|---|---|---|---|---|
| P-41 | feature | Fork with an upstream link: forking an app gives the downstream its own project, repo, database, files and bindings, and a link to the upstream; the upstream publishes versions as tags on a release branch; unlink (stops update notices, security ones included; can be linked again). | design 9.13 | L | **panel** (architect, security) for the release format and the contract, then **pipeline**; needs repos (step 4) or a minimal git store in step 3. |
| P-42 | feature | The update agent: on a new upstream version it merges on a draft, resolves conflicts with the customisations, runs tests and migrations on a database branch, and writes a summary; the downstream approves. Security updates marked and shown prominently, never applied without approval. | design 9.13 | L | **pipeline** after P-41. |
| P-43 | feature | Delegated approval: the downstream lets an agent apply updates within limits it sets (for example patch and security versions when tests pass and nothing conflicts); every update in history and the audit log, with a one-step revert. | design 9.13 | M | **brief** after P-42. |
| P-44 | feature | Extension points of a base app (extra fields and tables in the downstream schema, own views, automations on app events, role mapping, translations, theme, named hooks); the update agent reports which customisations caused conflicts. | design 9.13 | L | **panel** (architect, UX designer), then **pipeline**. First case: the TajuRuum work management app. |
| P-49 | feature | The agent channel between upstream and downstream: downstream proposals to the upstream (pull request model, agents discuss the code, upstream people approve into a version); upstream refactorings only of the code in a proposal (the upstream never sees the fork's source, schema, data, logs or secrets); pre-release versions that each fork's agent checks against its own code, reporting only what it chooses; summaries for people; either side can close it. | design 9.13 (the person, 2026-11-12) | L | **panel** (architect, security), then **pipeline** after P-42. |
| P-50 | feature | Aggregated usage statistics for the upstream: counts of declared configuration options, extension points and hooks in use, versions and channels, unlinked forks; the scope of changes outside the extension points (per file and directory of the upstream's tree: share of forks and lines added, changed, deleted in ranges; added files as totals per top-level directory, no names); across forks only, at least 5 per number; the downstream sees its contribution and can turn it off (on by default; a licence cannot require it); the upstream agent uses the numbers to announce and measure feature removal. | the person's idea 2026-11-12; design 9.13 | M | **panel** (security, privacy) for the counted set and the threshold, then **pipeline** after P-44. |
| P-45 | feature | Visibility of an app: public listed (directory with review), public unlisted, select tenants, tenant listed, tenant unlisted, select users, private. | design 9.13 | M | **pipeline** with P-41; the directory with review later. |
| P-46 | feature | Price models: free, one-time fee, subscription (per tenant, per seat, by use), and a trial with its own terms and length. | design 9.13, 21.7 | M | with P-48. |

## 2. Billing (design 21.7)

| ID | Kind | Item | Evidence | Effort | Handling |
|---|---|---|---|---|---|
| P-47 | feature | Level 1, Ruum bills its tenants: plans and usage (21.4), invoices with EU VAT (reverse charge, OSS), card and SEPA through Stripe Billing, receipts as files, dunning (reminders, read-only, no deletion without notice); card data never touches Ruum; billing events audited; agents see amounts and states only.
