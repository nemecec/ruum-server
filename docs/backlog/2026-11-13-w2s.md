# Backlog 2026-11-13, card W-2s review fixes

Items left by the review fixes of card W-2s (`s3/w-2s`), after the review
(`ruum-server-wt/panel/review-w2s.md`) and Kimi's review (`review-w2s-kimi.md`). The fixes are in
`review-w2s-fix.md`. The IDs are `W2S-n` so that they do not collide with the run backlogs. Kinds,
efforts (S, M, L) and handlings are as in `docs/backlog/2026-11-08.md`. All decisions here are
`provisional` (design 18.9).

| ID | Kind | Item | Evidence | Effort | Handling |
|---|---|---|---|---|---|
| W2S-1 | gap | Static site file objects (`apps/static/<tenant>/files/<hash>`) are never deleted: not for an expired, failed or superseded deployment, and not after the app is purged (STEP3 area 1: "purge = stop and delete images"). No tenant storage quota is checked before they are written, so repeated deploys of changed sites grow the bucket without a bound. Needs a mark over every index that may still be served (live, releases that can be rolled back, ready and running previews) with a grace period for indexes being written, a sweep of unmarked objects, index and object deletion on purge, and a quota check before `write_site`. | Kimi finding 5, review note "Static objects are never deleted"; seen again by Kimi run 10b (`kimi-w2s-r10b-checked.md` 5, medium), not fixed by `fix/w2s-kimi` | M | **pipeline**, apps area (with the erasure work). **Done** (branch `f/w2s-1`, `panel/impl-w2s1.md`): static objects count against the storage quota (a direct `403 quota_exceeded` before the `202`, checked again in the image stage under a tenant site lock); the garbage collection (`apps/static_gc.rs`) keeps live releases, earlier releases and open previews, deletes ended previews' and purged apps' indexes and then unnamed file objects after a grace period; the purge hook deletes an app's indexes at once. Review fixes (`panel/review-w2s1-fix.md`): index objects count (a publish or rollback whose index copy does not fit is a `403 quota_exceeded`), the quota error names only the needed bytes, no file is deleted while a recent pending or running deployment has no index (rolling upgrade), the collection runs in its own task and the purge hook only deletes the app's indexes. Left: W2S-3 to W2S-6. |
| W2S-2 | gap | The Postgres GC test (`postgres_gc_keeps_release_chunks_and_frees_ended_previews`) now takes its `chunks` rows from the store (`NewDeployment.new_chunks`), but no test runs `createAppDeployment` -> expire -> GC on Postgres end to end: the in-memory services have no chunk rows for deployments, and there is no Postgres `AppService` test world in `ruum-core`. Add one when a Postgres service world exists (or as a test kit case with a GC hook). | Review finding 3 (test part) | S | **pipeline**, test kit |
| W2S-3 | gap | File uploads (blob store `check_limits`) and `getLimits` count only node sizes, not static site objects. A tenant can use about twice its plan's storage: first through static sites, then through files; `getLimits` under-reports its usage. The static quota itself reads the usage without a lock (as the upload check does), so concurrent deployments of one tenant can exceed it by about one site each, and every deployment lists the tenant's objects to count them. | `review-w2s1.md` required 4a and notes, `review-w2s1-kimi.md` 3 and 5 | M | **pipeline**, apps and blob store: a recorded static byte total per tenant (a migration under the expand/contract rule, design 12.7), updated when objects are written and collected, read by uploads, `getLimits` and deployments; a reservation in it makes the quota strict. |
| W2S-4 | gap | Release retention. Every live release stays forever, because each one is a rollback target, so its index and files are never collected. A tenant that publishes many different releases fills its quota, and the only way to free that space is to purge the app; the quota hint ("delete ... apps you do not need") then points there. | `review-w2s1.md` required 4b, `panel/impl-w2s1.md` reviewer note 2 | M | **brief**: a retention rule (for example the last N releases stay rollback targets) or an operation that deletes a release; then change `StaticDeployment::reachable` in both stores. |
| W2S-5 | gap | Tenant erasure of static sites. The apps provider does not ask for the `tenant_deleted` hook (its descriptor names `copied`, `trashed`, `restored`, `purged`), so `apps/static/<tenant>/` and the app rows go only if the deletion of a tenant purges every app node first. Not checked by W2S-1. | `review-w2s1.md` required 4c | S | **pipeline**, apps area (with the erasure work): check the tenant deletion path; if it does not purge each app, handle `tenant_deleted` in the apps provider and delete the tenant's prefix. |
| W2S-6 | improvement | Scale of the static garbage collection. One run of a tenant holds the exclusive site lock while it lists and deletes every object, and holds the marked hashes of all kept indexes in memory; there is no time budget per tenant. A run longer than `SITE_LOCK_WAIT` makes the tenant's deployments fail with a generic `image_failed` (`sites_busy` is not mapped to a stage code), and the periodic run waits only 5 s for the lock, so a tenant that deploys without pause delays its own collection. | `review-w2s1.md` notes, `review-w2s1-kimi.md` 6 | M | **later**: batch the work or release the lock between the index and file phases, a time budget with resumption, a retryable stage code for `sites_busy`. |
