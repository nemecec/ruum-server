# Digest card Q-2 (2026-11-11): agents can query Postgres databases with a privacy filter

Short report for the person (design 18.9). Card Q-2 is on `main` now, after five rounds of
hardening and ten reviews. `main` is not pushed. Each decision is `provisional`, and you can veto
any part of it.

## What changed on `main`

18 commits of the branch `s2/q-2-harden-5`, rebased onto `main` (`4019de1`), checked on the build
server, pushed as `integq2/q-2`, green in GitHub CI, then fast-forwarded. The history is linear: no
merge commit, no co-author line. One fix of the integration: the migration of this card is
`0012_column_definition.sql`, because step 3 took `0011_apps.sql` on `main` first.

An agent can now run SQL on a Postgres database through `queryDatabase`, and it never sees a real
personal or secret value unless a person gave it a grant. The privacy suite, which was all planned,
runs its Postgres cases for real.

## The S-21 rule (decision 0004-38)

The first three reviews kept finding one more path: a trigger, a rule, a volatile function in a
view or a default that runs on the real row, started by an agent. Each fix closed one path and
the next review found another. The architect panel stopped that with one rule in design 8.5:

> A masked session never starts tenant code on live data.

If the database holds code that an agent's write would start, the write is refused with
`tenant_code_on_live` (HTTP 501), before and after the statement, in the query layer and again in
the engine. Reads still run through views, but see the allow-list below. A person with `manage`,
the owner kind and the users of an app are not affected: the rule removes the agent as the starter
of tenant code, not tenant code that others start.

## The allow-list (decision 0004-38 and 0004-39)

Code that runs on real rows may call only functions on a list: the built-in functions that are
safe, and nothing of the tenant or of an extension. The list covers views, policies, `CHECK`
constraints, generated columns, domain checks, index expressions, the support functions of the
operator classes of indexes, and the input and output functions of types. A view or table that
reaches anything outside the list gets a refusal in the masked lens. Volatile built-in functions
(`set_config`, locks, large objects, sequence writers) are revoked from the masked roles, and a
pooled connection is reset with `DISCARD ALL` between uses.

## The masked-view rebuild (decision 0004-39)

The fifth round replaced a growing list of guards with one structural rule:

> Masked sessions only ever see tenant views evaluated over masked inputs.

The lens view of a tenant view is now the definition of the view with its base tables replaced by
the lens relations of the same schema. A personal column is already a pseudonym there and a
secret column is already the hidden marker, so joins, filters, casts and row-producing functions
such as `generate_series` run on masked data, never on a real value. Equality joins and grouping
still work, because the pseudonyms are consistent. A view that cannot be rebuilt gets a refusal
view, in that lens only. A table whose policy reads a restricted column is refused, because a
policy cannot be rebuilt. Every `:relid` in the rebuilt tree must be a relation of the lens schema.

## What agents can do now

- Read any table or view of a Postgres database. Personal columns show as pseudonyms
  (`p_8f3a91`), secret columns as the hidden marker, `NULL` as `NULL`, and normal columns as they are.
- Compare, join, group and count on pseudonyms: equal values give equal pseudonyms.
- Read real personal values when a person gave a live `read_personal` grant. Secrets stay hidden
  for every agent.
- Write when a person gave a live `write_live` grant, and only to databases without tenant code that
  the write would start. Without the grant: `403` with the grant prompt. `DELETE`/`UPDATE` without
  `WHERE`, `TRUNCATE` and schema changes: `501`, nothing runs (card A-2 will add the approval).
- See `getDatabaseSchema` with the class that the lens applies to each column.

## Limits (stated, not hidden)

- **A masked reader can learn**: whether two values are equal, how many distinct values there are,
  how rows group and join, row counts, the fixed length of a pseudonym, whether a value is `NULL`
  (and facts computed from that), and everything in `normal` columns. Errors and the time of a
  statement can still depend on the real value that the lens reads to make a pseudonym.
- **Tenant code that others start can copy a restricted value into a `normal` column.** The agent
  that writes the code should suggest the right class; the `privacy` stage of the pipeline (step 4 or
  5) will check it. A narrow race stays: code that removes every trace of itself between the two
  engine checks.
- The lens view of a tenant view is read-only. A personal column of a view is the pseudonym of what
  the view computes, so it does not join to the pseudonym of the same value in a table. A table
  whose policy reads a restricted column is not readable by masked sessions. A view with arithmetic
  or a typed join on a personal column is refused for masked reads.
- **Not closed, in the backlog**: the labelling of values that come from catalogs outside the tenant
  schema (s21-2 N-1), the trait default for future engines (N-2), S-18, execution tests for
  foreign tables and event triggers, `current_setting` stays callable. Panel items S-20, S-22, S-23
  (decided strict in 0004-38 (h)), S-25, S-26 and P-29 (empty secrets) are unchanged.
- The type-function slots (modifier, analyze, subscript) of the allow-list have no test of their
  own. The rebuild is the protection; the list is defence in depth.
