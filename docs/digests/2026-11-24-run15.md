- **O-53, O-54, O-55: the edge after a reboot, `upgrade-talos.sh`, blob-copy** (`ops/o-53`, 2
  commits). An edge pod is ready only when it holds its certificates: an init container waits
  for the API server (it trusts the cluster CA; the review found that busybox wget verifies
  certificates, so the first version always waited 120 s), and readiness asks Caddy's
  `/_edge/ready`. The load balancer checks become HTTP(S) checks (`/_edge/alive` on port 80 via
  the new Service `ruum-edge-http`, NodePort 30081, with `publishNotReadyAddresses` so that a new
  cluster's first ACME HTTP-01 order does not deadlock; `/_edge/ready` over TLS on 443). Port 80
  stays on 30080 in `ruum-edge` for one release (expand, then contract; O-57).
  `upgrade-talos.sh` retries the API after a node reboot and checks each node's edge pod. The
  nightly blob-copy reads the buckets at their real location (fsn1) and keeps fewer failed Jobs.
  Charts, OpenTofu and scripts only; no Rust, no migration.
- **D-5: app role kinds of a binding** (`s3/d-5`, 6 commits). The data cluster engine makes the
  two app roles of a database binding, `app_read` and `app_write` (decisions 0004-14 and
  0004-32): one neutral role per (database, kind, binding) with the grants of the kinds table,
  SCRAM passwords with `VALID UNTIL` (the verifier is made in Rust, so the password never reaches
  the server's statement log), a connection limit and a per-tenant cap (20), the cluster app
  budget, `temp_file_limit` (credentials are refused while `ruum_dbhost` cannot set it, D5-3),
  and clean ends: a dropped role is stripped from other databases and restore points first
  (`REASSIGN OWNED`, `DROP OWNED`), and copies hand over without the source's app grants. A
  database in the trash suspends its app roles (`suspend_app_access`, `resume_app_access`; NOLOGIN
  and its sessions ended and checked). The core has `AppRoles` (`ruum-core`
  `databases/app_roles.rs`) and the provider's trash hooks call the engine. **Migration 0017**
  (expand only): `database_roles.kind` also takes `app_read` and `app_write`. Nothing hands out
  app credentials yet (B-1d). 12 new mutations.
- **I6-1 with S-83: the Kubernetes runtime driver** (`r/i6-1`, 7 commits). `KubeDriver`
  (`ruum-runtime` `src/kube`): one gVisor pod per run in `ruum-apps`, state in ConfigMaps with
  compare-and-swap, secrets in a Secret per instance that the driver writes but cannot read, a
  read-back of every pod it makes, the egress registration with an intent record and a confirm
  step, per-run gateway addresses, log redaction in the process that started the run, caps on
  instances and ended logs, and a sweep for orphans. It passes the unchanged runtime conformance
  suite (23 cases) against a fake API server with a fake kubelet, plus 7 driver tests and
  deterministic race tests. `ruum-server` wires it with `RUUM_RUNTIME_DRIVER=kubernetes` (11 new
  optional settings; the API URL must be `https://`, egress control only `unix:/`). Staging: the
  server's ServiceAccount and a Role in `ruum-apps` (no Secret read, no exec), and a
  ValidatingAdmissionPolicy that admits in `ruum-apps` only gVisor pods with no service account
  token, no host network, no init or ephemeral containers and no Secret but the pod's own (S-83;
  bound by the `ruum.instance` label, S-85). Node22 apps still answer the gateway's 502: deploys
  refuse `runtime: node22`, and staging has no builder or registry (I6-13).

No new external dependency (`ruum-server` now uses the workspace crate `ruum-runtime`;
`ruum-dbengine` uses the workspace crates `base64`, `sha2` and, in tests, `tracing-subscriber`;
`ruum-runtime` uses `axum` in tests). No contract change. No CI file change.

## Risks

- **No card of this run has a Kimi APPROVE on its final code** (S-78).
- **The Kubernetes driver is on by default with the app runtime** (chart `runtime.kubernetes:
  true`). The server pods name the new ServiceAccount, so the platform step must run before the
  deploy, or the server pods do not start (see below). It was tested against a fake API server
  only (I6-16); the first live start (I6-13) may refuse a pod on an API server default that the
  read-back does not expect. That fails closed, and the error names the field.
- **Staging writes blobs to the wrong endpoint** (O-56, found by O-53, not fixed): the server
  uses hel1 while the buckets are in fsn1, so blob and static site writes on staging most likely
  fail today. The smoke checks do not upload a file.
- **The O-53 load balancer change**: if Hetzner verifies the backend certificate on the HTTPS
  check (staging may run the Let's Encrypt staging CA), the 443 targets turn unhealthy right
  after the apply; step 6 below checks this within a minute and says how to revert. A rollback
  below O-53 after the tofu apply stops port 80 (redirects, HTTP-01) until the LB goes back to
  30080; the release floor does not refuse it yet (O-58).
- **D-5 adds engine work on a database trash and purge**: the trash hook suspends app roles
  (NOLOGIN; a lazily made table `ruum_meta.app_access` in the database). No app roles exist yet,
  so on staging this is a no-op beyond the table. A role left by a failed `drop_orphans` stays
  (NOLOGIN) and counts against the app budget (D5-14).
- **Migration 0017** widens a check constraint (expand only); the previous release never writes
  the new values and does not parse the kind.
- GitHub CI's Docker memory checks failed twice in a row on `integ15/i6-1` (T-75); a red run of
  that job can hide a real failure in the same job.
