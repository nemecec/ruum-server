# Digest run 13 (2026-11-19 to 11-20): step 3 wave 5 (telemetry processor, bindings, Node SDK) and two follow-ups

Short report for the person (design 18.9). This run built three step 3 cards: the telemetry
processor role (O-1b), bindings without database bindings (B-1) and the Node SDK (O-5); and two
follow-ups: the site purge at scale (W2S-4, from the run 12 Kimi re-check) and Talos changes
through the staging admin tunnel (O-21). All five are merged. Each panel decision is
`provisional`; you can veto any part. `main` is not pushed: the orchestrator pushes and deploys.

## What changed on `main`

Five branches were rebased onto `main` `5267efc` in one stack, each tip checked on the build
server, pushed as `integ13/<name>`, green in GitHub CI, then fast-forwarded in this order
(`5267efc..99311f5`), plus this documentation commit. The history is linear: no merge commit, no
co-author line. One rebase conflict: B-1 and W2S-4 both added a conformance case, a memory store
field and a table name to the app store tests; both are kept. No migration was renumbered: B-1
had taken `0016` because W2S-4 uses `0014` and `0015`.

- **W2S-4: the site purge at scale.** Deleting a big app's static sites no longer reads every
  row of the tenant. It pages through the app's own deployment rows and stores its cursor
  (new table `app_purge_progress`, migration `0014`) before every wait on the object store. Delete
  requests start with one key and double, so a slow S3 bulk delete cannot stop progress (Kimi
  finding 1). The new index is built with `create index concurrently` outside a transaction
  (migration `0015`, Kimi finding 2), so deployment writes are not blocked during the upgrade.
- **O-1b: the telemetry processor role** in `ruum-server`, off unless `RUUM_TELEMETRY=on`. It
  takes OTLP (logs, metrics, traces) over HTTP and gRPC from app sandboxes, knows the sandbox by
  its network address (never by what the data says), runs the O-1a privacy pipeline and writes to
  Loki, Mimir and Tempo, one store tenant per Ruum tenant. A log shipper takes the sandboxes'
  stdout the same way. The review fixes bound the decoded size before decoding, check gRPC
  callers before reading the body, hold each tenant's in-flight bytes from the first byte, and
  rotate the shipper between instances. Not wired to app networks yet (I-4, I-6).
- **B-1: bindings.** An app's `bindings` in `app.yaml` (folders, files, APIs; not databases)
  are checked against the deployer's rights, written as rows and SpiceDB tuples for the preview
  and the live app, and ended when a binding is dropped, a preview is superseded, the app is
  trashed or the target is gone; a repair pass fixes tuples that drift. The app sees its targets
  as `RUUM_BINDING_<NAME>`. The journal now writes `app.binding_granted` and
  `app.binding_revoked`. Migration `0016` drops the foreign key on the binding target, so purging
  a bound folder no longer fails on Postgres (review blocker; one bound root blocked "empty trash"
  for the whole tenant).
- **O-5: the Node SDK** (`sdk/node`): `@ruum/app` checks the gateway's `Ruum-User` token
  (Ed25519, the schema of `user-token.schema.json`), calls the platform through the egress
  proxy and has a dev mode that refuses to run in production; `@ruum/log` drops secret fields;
  `@ruum/eslint-plugin` flags secrets in log calls. Rust checks the SDK's token vectors against
  the real gateway signer. Not published to npm.
- **O-21: staging Talos access.** Talos changes and a fresh create of the staging cluster go
  through the admin tunnel, also after a stopped bootstrap. Code only: nothing was applied to
  staging, and the read-only live plan shows no change.

New dependencies (O-1b, approved in decision 0006 E-5 and F): `opentelemetry-proto` 0.33.1,
`prost` 0.14.6, `tonic` 0.14.9 (with `opentelemetry`/`opentelemetry_sdk` 0.33.1, `tonic-prost`,
`hyper-timeout` transitively). O-5 adds only npm dev dependencies inside `sdk/node`.

## Risks

- **No card of this run has a finished Kimi APPROVE** (S-70). B-1 and W2S-4 change what the
  server does on staging with this deploy (binding rows and tuples, the purge of app sites).
- B-1 writes two new journal types. Under design 12.7 (P-57, P-89) it may ship only after
  staging runs a release whose readers pass unknown types (`901bfaa` with the Kimi fixes up to
  `2303216`, both on `main` since run 12). If staging still runs a release older than that, old
  pods during the rollout fail the changes feed on these entries.
- Migration `0015` is a `-- no-transaction` migration with `create index concurrently`. If the
  step is cut, the index can stay INVALID and the next step fails on "already exists"; the file
  comment gives the repair (`drop index concurrently app_deployments_app_id_idx`, then run the
  step again). It waits for older open transactions in the database.
- The telemetry role is off by default; it has no header timeout or connection limit yet
  (S-71), and its memory must be sized from about 2 x 256 MiB in flight (P-100) when it is turned on.
- The changes feed property test fails on a known seed on `main` (T-58), seen once at random in
  CI; it is older than this run.
- Build server: the data cluster still drops under a full workspace run beside mutation shards
  (B-39, B-42); timing tests fail under load (T-54, T-59).
