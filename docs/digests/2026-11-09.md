# Digest 2026-11-09: the SQLite advisory, the masking fix, untrusted agent text, Estonian "Ruum", card Q-1

Short report for the person (design 18.9). The integration ran on 2026-11-09, in two tries.
Agent panels decided everything here. Each decision is `provisional`, and you can veto any part
of it. `main` is not pushed.

## What changed on `main`

Five branches were rebased onto `main`, checked on the build server, pushed and checked in
GitHub CI, then fast-forwarded, in this order (`3656b80..24d192b`, 12 commits, plus this
documentation commit). The history is linear: there is no merge commit and no co-author line.

- **The SQLite advisory** (`d/rusqlite-0.41`, new). RUSTSEC-2026-0459 (CVE-2026-119375,
  published 2026-10-30): SQLite before 3.54 can return uninitialized memory when it opens a
  database with a `-wal` file of another page size. `rusqlite` 0.39 bundled SQLite 3.53. It
  failed `cargo-deny` on every branch and on `main`. Now `rusqlite` 0.41.1 bundles SQLite
  3.54.1. One snag: sqlx 0.9.0 (the newest) has an optional SQLite driver that asks for the
  old `libsqlite3-sys`, and Cargo allows only one crate that links `sqlite3`, even when the
  driver is never built. A small empty stand-in for that driver
  (`third_party/sqlx-sqlite-stub`, through `[patch.crates-io]`) solves it. Ruum uses sqlx only
  for Postgres. Remove the stand-in when sqlx releases the fix it already has on its `main`.
- **The masking hole is closed** (`f/masking-hardening`, decision 0005 B-2 and 0004-37,
  backlog S-1 and S-4). A tenant's own types never reach a definer function of `ruum_mask` any
  more (such a personal column is masked like `secret`). Every lens build makes the objects of
  `mask` again, and a restore in place repairs the restored copy before the swap.
- **Agent-written text is marked untrusted** (`f/untrusted-agent-text`, decision 0005 B-3). 52
  fields in the contract carry `x-ruum-content-trust: untrusted`. 62 of 70 MCP tools tell the
  agent to treat such text as data, never as instructions. No wire change.
- **Estonian "Ruum" and "ruum" apart** (`w/et-ruum`, decision 0005 B-1). A new rule in the
  translation check, 12 Estonian messages rephrased, the style guide updated.
- **Card Q-1, the query API for people** (`s2/q-1`, head `s2/q-1-fix2`). `queryDatabase`,
  `getDatabaseSchema` and `listDatabaseQueries` are built (12 of 24 database operations now).
  The data cluster set-up revokes `set_config` from `PUBLIC`, the engine refuses a database
  where `PUBLIC` can still run it, and the names middleware leaves query rows alone.

Fixes made at the integration:

- The first try stopped before any merge: the build server was not reachable (the laptop's IP
  changed and the firewall allows one IP), and the advisory appeared. The advisory fix landed
  first, and the stack was rebased onto it.
- The masking tests used `set_config` as a hit marker, which Q-1 takes away from the masked
  reader. The marker is now an owner-kind definer function (in the Q-1 commit).
- The build server's shared data cluster runs the set-up of Q-1 now.

## The security reviews

- **Masking** (`f/masking-hardening`), three reviews. Review 1 accepted, with two notes that do
  not block (F1: the wording "`mask` cannot change the lens" went too far; F2: step 2 of a masked
  copy can leave objects that point into `ruum_mask`). Review 2 did **not** accept: F-1, the
  state from before the fix survived a lens build, and `restore_in_place` brought it back (a
  probe proved it). The fixer closed F-1 and the notes with one design: every build drops and
  makes the lens schemas again after a dependency check (`masking-fix-2.md`, four new
  mutations). Review 3 **accepted** (`review-masking-3.md`). Its notes: a database from before
  the fix keeps its pseudonym key (optional: rotate the key before Q-2 serves masked reads; the
  pseudonyms then change); no repair path for an old foreign dependent (fails closed); test
  placement; mutations over the whole suite need fewer test threads.
- **Q-1** (`s2/q-1`), three reviews. Reviews 1 and 2 asked for changes; review 2 found S-1
  (`set_config` through `query_to_xml` and `ts_stat`). After two fix passes, review 3
  **accepted** (`review-Q-1-3.md`): no path to `set_config` for a read, write or masked kind, no
  names in query rows. Notes for the panel: N-A (the owner kind can still change options,
  as it can through a function's `SET` clause) and N-B (`UPDATE pg_settings` passes the rules
  as `Write`; the engine refuses it, but with another error than the contract's).
