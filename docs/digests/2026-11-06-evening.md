# Digest 2026-11-06 (evening): first push, CI green, three leaks fixed

Short report for the person (design section 18.9). You can veto any `provisional` decision.

## What happened

- **First push** to <https://github.com/nemecec/ruum-server> (public, Apache 2.0). The history was
  rewritten before the push: linear (no merge commits), Neeme Praks as author, no Claude
  co-author lines, the GitHub LICENSE commit first. A secret scan (gitleaks) over the whole history
  found only false positives (a content hash and test placeholders).
- **CI ran for the first time and is green** on `main` (all 8 jobs, three runs in a row). Getting
  there needed four fixes of the CI setup, none of them in the product:
  - the unit tests ran as the Postgres superuser, which bypasses row-level security; they now run
    as a role without superuser, which may create the sqlx test schema;
  - the visual tests had references for macOS only; the Linux references now come from CI, and
    all runners are pinned to `ubuntu-24.04` so they do not drift;
  - one browser test set an upload before the opened folder was shown (timing in the test);
  - the MCP tool list was out of date after the license change in the OpenAPI file.
- The security suites now treat an unbuilt operation (501) as a failure by default.

## Real bugs found by the property tests

The changes feed property test found, on CI, a case that the laptop runs never generated. More
cases (2000 per run) found more. All are fixed, with unit tests, conformance tests (memory and
Postgres), saved regression cases and mutation rules:

1. An agent got a `node.purged` entry, with the node's name, for a node it never saw (its scope
   allowed only `edit`, and a node in the trash shows only to who may restore it).
2. A guest who got access to a folder after an item in it was trashed got that item's name.
3. The same for any access that began after the trash, through the folder that held the item.

**New rule, decision [0002-6](../decisions/0002-step1-panel-decisions.md) (provisional):** an entry
about a trashed or purged item reaches only who could see it just before the trash, or who could
restore it while it was in the trash. Access that began later never reveals it.

The chunking property test also failed now and then. That was the test, not the chunker: it was off
by one byte at the insert point, and it assumed that chunks line up again within 256 KiB after an
insert, which FastCDC does not promise (measured: median 27 KB, 90% within 97 KB, maximum 315 KB).
The property now tests the real guarantee, and a fixed-seed test checks that most inserts line up
again within 128 KiB.
