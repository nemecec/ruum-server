- **S-35: random slugs for personal workspaces** (`s3/s-35`, your decision 0008-1). A personal
  workspace gets a neutral slug such as `ws-7k2m9q`, never one from your name. You can choose a
  readable slug once, on the Admin page; the page says that the slug is public (DNS, certificate
  logs) and permanent. The choice is in the audit log (`tenant.updated`). Team workspaces keep
  name-based slugs, and a taken name gets a random suffix instead of `-2`, `-3`, so the numbers no
  longer reveal other workspaces. Existing personal workspaces on staging keep their old slugs.
- **T-6: the test harness of the app gateway** (`s3/t-6`). 49 gateway cases and 13 runtime API
  cases, written before the code: who may open an app, tokens, sign-in on an app's own address,
  security headers, static files, credentials that must never cross tenants, smuggled requests.
  A deliberately wrong toy gateway proves that each case can fail, and why.
- **W-2s: static app deployments** (`s3/w-2s`). Upload a site as a file or folder archive,
  publish it, roll it back. Only a person can make a site live; an agent gets an approval
  request. Source maps are never served. Slugs of deleted apps are never given again.
- **B-2: app roles** (`s3/b-2-r1`). An app declares roles (for example `member`, `approver`,
  `admin`); people get roles; the roles that count follow the live version of the app.
- **G-1a: the app gateway** (`s3/g-1a-r10`). The new service `ruum-gateway` serves apps on
  `<app>--<workspace>.<apps domain>`: sign-in on the app's address, app sessions, the access
  check on every request, a per-app user token for the app, static files. It has its own narrow
  database role (it may only run one lookup function). All T-6 gateway cases pass, except the
  three role cases (see "Risks"). The gateway is **not deployed** yet (that is card I-6).

## What the orchestrator must do to deploy

Staging runs the `main` of run 9 plus the Kimi re-review fixes (or later). Run everything from
the main checkout on the Mac at the new `main` (O-34 is not merged, so the deployer stays on the
Mac).

1. Gitleaks on `origin/main..main` (exit 0), then push `main`. Wait until the `ci` and `images`
   workflows pass on the push (`deploy.sh` checks both).
2. **No new secret, no platform step, no new server setting, no chart change.** The new
   settings (`RUUM_GATEWAY_*`, `RUUM_APPS_DOMAIN`) belong to `ruum-gateway`, which is not
   deployed (card I-6; `docs/backlog/2026-11-14-g1a.md` G1A-4 lists what it needs).
3. `deploy/staging/deploy.sh <sha of the new main>`. **There is one new migration,
   `0013_app_host_lookup.sql`**, so `deploy.sh` takes its backup first, then the migration Job
   (as `ruum`) applies it before the rolling update. It is expand only: a `SECURITY DEFINER`
   function and the tables `app_sign_in_codes` and `app_sessions`; the previous release uses none
   of them. It creates the role `ruum_gateway` only when the migration role may create roles; on
   CNPG it may not, so it skips that part and the grant (no error). `ruum_app` gets its rights on
   the two new tables through the default privileges of `ruum`.
4. `deploy/staging/status.sh --checks`.
5. Rollback: `deploy.sh <previous sha> --rollback`. The old release runs with the new schema
   (expand only). The new tables and function stay; nothing reads them.
6. After the deploy, the API has the app deployment and role operations. Their journal event
   types (`app.deployed`, `app.deployment_failed`, `app.rolled_back`, `app.role_granted`,
   `app.role_revoked`) are new: during the rollout, an old pod's changes feed fails on such an
   entry (P-57). Nobody deploys apps on staging, so this is acceptable once.
