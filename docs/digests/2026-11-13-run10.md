**How `deploy.sh` works now:** it checks on the Mac (CI on main, digests, provenance, order,
the O-25 floor, chart drift against the controller's commit), then only writes a release request
and waits for its outcome (`Succeeded`, `Failed` or `Refused`; exit 0 only on `Succeeded`). The
controller decides the backup, runs the migration Job and `helm upgrade
--rollback-on-failure --wait` with its own ServiceAccount. The chart, the migration Job and the
deploy scripts come from the controller's image (the commit of the last platform step), not from
the checkout or the target: a later chart change reaches staging only through a platform step
from a checkout that has it, then a deploy (`deploy.sh` warns). `deploy.sh --rollback` goes back
one release (the recorded `previous`); `--rollback-older` stops on the Mac, because the
controller refuses it (Kimi O-34 #1): an admin runs it in the controller's pod (README "Going back
past the previous release").
