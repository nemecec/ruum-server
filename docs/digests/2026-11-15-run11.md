## What changed on `main`

Four branches were rebased onto `main` in one stack, checked on the build server, pushed as
`integ11/...`, green in GitHub CI, then fast-forwarded, in this order (`616e34e..4d991cc`, plus
this documentation commit). The history is linear: no merge commit, no co-author line.

- **A dependency notice, handled by the integrator** (`integ11/deny-chrono`). On 2026-11-16
  RustSec declared the date library `chrono` unmaintained, with no upgrade. That failed the
  supply-chain check (`cargo-deny`) on `main` and on every branch. Ruum's own code does not use
  chrono; three libraries we use do (WebDAV, object storage, MCP). The integration added the two
  notices to the ignore list with a reason. This is a notice, not a vulnerability. **You may want
  to confirm it** (backlog O-52).
- **R-2e: the egress proxy** (`ruum-egress`, a separate binary and image). It is the only way
  from an app's sandbox to the internet. It allows only HTTPS tunnels, checks the address after
  the name is resolved (no private, loopback or cloud-metadata addresses, no address inside
  another app's network), applies per-app allow lists, limits and byte counters. The review fix
  identifies each connection at once and caps it per app, so one app cannot use up the shared
  limit with slow requests.
- **R-2a: the Docker runtime driver** (`ruum-runtime`, new dependency `bollard` 0.21.1, the Docker
  API client). It runs an app's container with plain Docker or with gVisor (`runsc`): a private
  internal network per app, a read-only root, no extra mounts (images that declare volumes are
  refused), memory and CPU limits, logs with secrets hidden, the egress proxy as the only exit. A
  hostile sandbox suite tries to escape (network, files, kernel, resources); every row passes on
  both runtimes. Cold start: about 0.6 s on both. S-36: the log redaction now costs linear time
  and the number of secret values per app is capped.
- **I-5: the telemetry stack on the laptop** (`scripts/dev.sh up --apps`): Loki (logs), Mimir
  (metrics), Tempo (traces) and an OpenTelemetry Collector, each separated by tenant. The review
  found that Tempo answered a query for two tenants at once by default; that is now off in all
  three stores and checked by `scripts/telemetry_check.sh`.

Not merged: **O-1a** (the telemetry privacy core: classes, deny list, secret matcher, privacy
suite). Its second review asks for two more changes, from a Kimi verdict that arrived after the
first fix agent had stopped reading (backlog S-58).

## What you may want to decide

1. **The chrono notices** (O-52): keep the two ignore lines in `deny.toml` until the libraries
   move off chrono, or ask for another route.
2. **gVisor and Docker's seccomp profile** (R2A-2): without `--oci-seccomp`, gVisor does not
   apply Docker's seccomp profile inside the sandbox (gVisor's own kernel still separates it from
   the host). Turning it on forbids user namespaces, which decision 0006 G wants for builds. A
   choice per pool (apps, builds) for I-6.
3. **Secrets in the container config** (R2A-3): app secrets are environment variables, visible to
   whoever can read the engine API. I-4 must give the engine API to the server only. Moving
   secrets to files would change how apps read them.
4. **Kimi for R-2e and the R-2a fixes** (S-54): schedule both before I-4 runs the proxy.

## Risks

- The driver and the proxy are tested on the build server and in CI but not wired: `wiring.rs`
  still uses the in-memory driver. The real risks come with I-4: two server replicas on one
  Docker engine (review note A, S-56), restart reconciliation (R2A-1), engine faults that no
  test injects (R2A-8).
- R-2e has no second-model review yet (S-54).
- One tenant could take a large share of the egress proxy's global connection cap (S-55).
- The CI tenant isolation job takes about 40 minutes per branch (T-51).
- Unmaintained `chrono` stays in the dependency tree through three libraries (O-52).
