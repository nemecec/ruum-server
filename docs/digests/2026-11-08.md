## Security review

The `ruum_dbhost` search-path fix (`f/rr-fix-e2`, merged in the evening without a review) got
two reviews in this run:

- `review-dbhost.md` (`secrev`): **not complete**. The code reading confirms the fix
  (`search_path = pg_catalog, pg_temp` as a startup option on every `ruum_dbhost` session; a
  reset keeps it). The tests it asked for did not run.
- `review-dbhost-2.md` (`secrev2`): **not accepted**. It ran the tests on the build server:
  the search-path fix holds, and its mutation and both one-path variants are killed. But it
  **confirmed a serious hole elsewhere** (item 2): a tenant that runs a migration can create a
  cast from its own type to `text`. The pseudonym function `ruum_mask.pseudonym_other` is
  `SECURITY DEFINER` and owned by the role `mask`, so the tenant's function runs as `mask`. It
  can read the HMAC key and replace `ruum_mask.hmac12`, which shows every personal column in
  clear text to every masked reader, without any sign. Two test gaps stay open (item 1: steps 1
  and 3 with tenant types, casts, domains and default privileges; item 3: a reused admin
  connection after `RESET ALL`).

Today no agent reads through the lens (Q-2 and Q-3 are not built, and Q-1 masks every agent
cell), so nobody can use the hole against a person's data yet. It must be closed before Q-2.
Backlog S-1 and S-4 are the next security card; decision brief B-2 asks you for the masking
rule of tenant-defined types.

## The backlog and decision briefs

`docs/backlog/2026-11-08.md` is the first backlog of the product loop (design 20). The triage
agent read the 13 retro files of this run and the integrator's own retro, merged the duplicates
and sorted 59 items into six groups: security and privacy (7), step 2 product and contract
bugs (9), tests and CI (11), build server and review tools (12), method and docs (13),
translation (7). Most are small and go into the pipeline without a person; the clear ones are
the "Next cards" of `docs/STATUS.md`. Four need the architect panel (P-1, P-4, P-5, P-9). Three
need you:

### B-1. "Ruum" the product and "ruum" the space, and two glossary words

- **Problem**: in Estonian, "ruum" is the everyday word for a space (a team space, a personal
  space). The product is called Ruum. Running text like "Ruum ei saanud..." reads as "the room
  could not...". The old translation used it in about 15 messages. Two glossary choices also
  have no owner: "run" (of an agent's changes) is now "tööhoog", and plan names (Free,
  Personal, ...) stay English inside the Estonian UI.
- **Evidence**: `retro-copy.md`; `docs/ux/style-guides/et.md` section 2.
- **Options**: (a) keep the product name out of running Estonian text (the style guide does
  this now) and keep "ruum" for a space; (b) use another word for a space (for example
  "tööruum") so that "Ruum" is only the product; (c) write the product name in a fixed form
  ("Ruum-i rakendus") where it must appear.
- **Recommendation**: (a) now, and look again with the first Estonian users. Keep plan names in
  English (they are names, as in the English UI); keep "tööhoog" until a person finds a better
  word.
- **Cost**: none for (a); (b) is one translation pass (about 1 hour of agent time).
- **Risk**: (a) means the product rarely names itself in Estonian.

### B-2. The masking rule for tenant-defined types

- **Problem**: the security hole of `review-dbhost-2.md` item 2. Engineering can harden the
  definer functions (pipeline, backlog S-1), but one part is a privacy rule: how does the lens
  show a personal column whose type the tenant made (an enum, a domain, a composite, a range)?
- **Options**: (a) such a column is masked like `secret` (a fixed marker, no pseudonym), so no
  tenant conversion ever runs in a definer context; (b) pseudonyms through the type's output
  function, called outside the definer context: keeps joinable pseudonyms, more code and more
  to review; (c) refuse a migration that makes a cast from a type used in a personal column:
  breaks normal tenant schemas and does not cover every path.
- **Recommendation**: (a). It is simple, it fails closed, and enums of personal data are rare.
- **Cost**: one card with the hardening (about half a day of agent time and two security
  reviews).
- **Risk**: agents cannot join or group on the pseudonym of such a column.

### B-3. Text that one agent writes and other agents read

- **Problem**: the reason of a column class suggestion is free text from one agent, and every
  viewer reads it, other agents too (through `list_database_columns`). It is a channel for
  prompt injection between agents (review-K-1 N-6). More such fields will come (approvals,
  issue nodes).
- **Options**: (a) mark these fields as untrusted in the contract (an additive
  `content_trust: untrusted`, as for file content) and say so in the MCP tool texts; (b) allow
  only a fixed list of reasons; (c) leave it.
- **Recommendation**: (a), as one rule for every agent-written field.
- **Cost**: small (an additive contract change and tool texts).
- **Risk**: (a) relies on the reading agent to respect the mark.
