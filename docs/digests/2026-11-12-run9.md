## Risks

- **First deploy with O-25 is not zero-downtime.** The edge changes from a Deployment to a
  DaemonSet (a short gap), and certificates are issued once more into the new storage.
- **Rolling deploys and new event types (P-57).** This run adds `database.approval_decided` and
  `app.settings_changed`. During a rollout an old pod's changes feed fails on an unknown type.
  Staging has no real users, so this is acceptable once; the journal fix needs two releases.
- **Drain race (O-30):** a POST at the moment a server pod drains can get a 502.
- **TLS keys in etcd (S-40):** confirm Talos encrypts Secrets at rest on staging.
- **The Postgres permission matrix is slow** (40 to 70 minutes; T-37), and the build server's data
  cluster (768 MiB) is OOM-killed when several suites run at once (B-29); this run saw both.
- **Step 3 security is still mostly on paper**: R-1's driver is in-memory, the gateway is a spike.

### What the orchestrator must do to deploy

Staging runs `3badfb0`. The database role split must reach the cluster **before** the deploy:
the new chart's migration Job reads `ruum/ruum-migrate-db`, which only the platform step writes.
Run everything from the main checkout on the Mac at the new `main`.

1. Gitleaks on `origin/main..main` (exit 0), then push `main`. Wait until the `ci` and `images`
   workflows pass on the push (`deploy.sh` checks both: the `ci` run and the provenance of the
   two image digests).
2. `git pull` in the main checkout (if the push came from elsewhere).
3. `deploy/staging/secrets-init.sh`. It adds `STG_PG_RUUM_APP_PASSWORD` to `secrets.env` and
   prints the name only. This is the only new secret.
4. **Platform step:** `RUUM_STAGING_APPLY=yes deploy/staging/secrets-push.sh platform`. In
   order: the Secret `data/pg-role-ruum-app`; the `platform` release (CNPG makes the role
   `ruum_app`; the deployer Role gets `leases` create and get/update on `ruum-deploy`); a wait
   (up to 5 minutes) for the role; the grants (`k8s/sql/ruum-runtime-grants.sql`, as superuser on
   the CNPG primary, which fails loudly if `ruum_app` could change the schema); then
   `ruum/ruum-migrate-db` (owner DSN) and, last, `ruum/ruum-server-env` with `ruum_app`'s DSN.
   The live `3badfb0` pods keep serving with their old environment. A pod that restarts now logs
   in as `ruum_app`, which already has its rights (`3badfb0` does no DDL while it serves).
5. Check: `deploy/staging/tool.sh kubectl -n data exec <primary> -c postgres -- psql -d ruum -tAc
   "select has_table_privilege('ruum_app', '_sqlx_migrations', 'INSERT')"` prints `f`. The
   primary is `pg-1` unless CNPG failed over
   (`kubectl -n data get cluster pg -o jsonpath='{.status.currentPrimary}'`).
6. **Deploy:** `deploy/staging/deploy.sh <sha of the new main>`. The deploy takes the Lease
   `ruum/ruum-deploy`. There is no new migration, so no backup is taken. The **migration Job**
   logs in as `ruum` through `ruum-migrate-db`, applies nothing and takes the write rights on
   `_sqlx_migrations` from `ruum_app`. Only when the Job succeeds does the **rolling update** start
   (`helm upgrade`, two replicas, `maxUnavailable 0`); the new pods log in as `ruum_app`. The
   deploy writes `previous = 3badfb0` into `ruum-release` for the first time, then runs the smoke
   checks. If step 4 was skipped, the Job stops with `CreateContainerConfigError`,
   `deploy-chart.sh` says "run the platform step", and nothing rolls out.
7. `deploy/staging/status.sh --checks`.

Rollback after step 6: `deploy.sh 3badfb077e25072ac05698969ba1eb84340644c6 --rollback`. Step 6
records `previous` from the live `ruum-release` (`3badfb0`), so a plain `--rollback` should pass
`ruum_rollback_target_ok`. The README and `impl-k9o25.md` say it needs `--rollback-older` this
once; that is the cautious reading (backlog O-38). If `--rollback` is refused, use
`--rollback-older`: nothing between `3badfb0` and the new `main` is a schema change. It uses this
checkout's chart, so its Job logs in as `ruum` and its pods as `ruum_app`. Never deploy from an
old checkout after step 4: its chart's Job reads `ruum-server-env` (now `ruum_app`, no CREATE) and
fails at `CREATE TABLE IF NOT EXISTS _sqlx_migrations`; nothing rolls out. To undo the role split
itself: the platform step from a checkout before `b6b0aef` writes the owner DSN back into
`ruum-server-env`; then `deploy/staging/tool.sh kubectl -n ruum rollout restart
deployment/ruum-server`. The same steps are in `deploy/staging/README.md`, "Moving an existing
staging to the two database roles".
