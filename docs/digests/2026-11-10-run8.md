## The step 3 specification, in short

Step 3 lets a person or an agent build a web app on Ruum: a static site or a Node.js app, with a
database from step 2, sign-in through Ruum, roles, previews and publishing, logs and error
reports. The plan is in `docs/STEP3.md`, the decisions in `docs/decisions/0006-step3-spec.md`,
the screens and texts in `docs/ux/apps/`.

- **Contracts, as drafts**: an app manifest, a gateway and a runtime API for apps, a user token,
  45 new REST operations (all marked `planned`, so nothing is offered yet), 35 MCP tools (not
  offered), authorization rules for apps, 21 event types and a draft migration `0011_apps.sql`.
  The test kit already knows every new operation, so tenant isolation and permission checks will
  run the day an operation is built.
- **The security model** (decisions 1 to 5, 10, 15): the internet-facing gateway holds no tenant
  keys. App code never gets more access than the person who uses it. An agent's publish waits for
  a person. Previews never touch live data. Agents never handle secret values in step 3.
- **Milestones**: M1 a static app deployed over MCP; M2 a Node.js app with logs; M3 the template
  "web app + Postgres + sign-in" with preview and publish; M4 error reports, issues and receipts.
  M1 and M2 do not wait for step 2. M3 waits for step 2 cards D-2 (which waits for A-2), a split
  of D-3 and a new D-5.
- **Reviews**: two architect reviewers asked for 30 changes; all are in the revision. The revision
  had no second review. The UX package has no UX panel review yet.
- Your decision 0007 (after the TajuRuum survey) says step 3 is where the customer's value is
  (the work management app as the first template). The spec was written before 0007; the first
  template in the spec is generic ("web app + Postgres + sign-in"). The next step 3 planner should
  make the TajuRuum app the first real template.

## Decisions that wait for you (decision 0006, section E)

None of them blocks the first cards. Each has a recommendation:

1. **E-1, the Public Suffix List entry for `ruumapps.net`.** Register the domain and ask for the
   PSL entry before the first public app, so apps of different tenants cannot share cookies.
   Inclusion takes weeks. Until then apps are visible only to signed-in members.
2. **E-2, the free tier's app limits.** Both reviewers suggest 3 apps, 256 MB, 1 instance, scale
   to zero, 7 days of telemetry and previews, no public apps, as configuration.
3. **E-3, who the platform admins are.** You alone at first, in a separate Zitadel organisation
   with passkeys only, on an origin apart from `ruum.space`. Needed before any public app or
   custom domain.
4. **E-4, publishing the SDKs to npm** (`@ruum/app`, `@ruum/log`). Agents prepare them; you
   publish when the API is stable (it needs an npm organisation).
5. **E-5, new binaries and dependencies**: Railpack (the Node.js builder), a Docker API client,
   OTLP and `tonic` for telemetry, a database pooler image. Approve them as provisional; each card
   names the exact version.

## Risks

- **Step 3 is large** (about 40 cards) and its data milestone waits for Q-2 and A-2 of step 2.
  Q-2 is still in its fix rounds (run 7). Decision 0007 says catalogues (tables with no personal
  columns) come first; that path does not need Q-2 and could unblock M3 earlier.
- **The step 3 security model is reviewed on paper only.** Sandboxing untrusted app code (spike
  S-2: rootless BuildKit, the egress proxy) is the riskiest part, and nothing has run yet.
- **A-2 waits**, so D-2 and the migration path of both steps wait too.
- **SQLite backups**: 24 hours of history instead of 7 days, one S3 key for blobs and replicas,
  and Litestream on macOS cannot share locks with a writer on the host (P-30, S-30, P-31).
- `main` is 12+ commits ahead of GitHub and not pushed.
