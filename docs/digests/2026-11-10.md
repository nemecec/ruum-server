  `integ7/wave5`). A database (a typed node) lives in a folder. When a person copies a folder

  agent**, also an agent that acts for a manager. Trash, restore and purge of a database tell its

## The Q-2 security reviews and the outcome

Card Q-2 is the privacy filter for agents' database queries on Postgres: an agent sees
pseudonyms instead of personal values and a constant instead of secrets (decision 0005 B-2).
It had three defensive reviews by Ruum's own reviewer agents:

1. **Review Q-2-1 (database side): changes requested.** Five holes, confirmed with probes on
   the data cluster. Two gave raw values to an agent **without any grant** (a view replaced in
   place kept its "normal" class; a manifest change did not rebuild the lens). Three gave raw
   secrets to readers without `manage` (a whole-row reference, a nested definer function, a
   generated column).
2. **Review Q-2-2 (privacy side): changes requested.** Tenant triggers copied raw values through
   an agent's write, error messages carried raw values in "object names", and the column
   footprint was easy to step around.
3. **The fix closed all 14 findings**, each with a test (CI green on the branch).
4. **Review Q-2-3 (final): changes requested.** All 14 are closed, but it found a new leak of
   the same kind (R-1): a tenant function behind a view runs on the real row when an agent writes
   a row, and can copy a secret into a table the agent may read. It was confirmed on a local
   Postgres. Also, 43 mutations of the fix were never run strictly, because the build server
   could not be reached.

**Outcome: Q-2 stays out of `main`.** Next: close R-1 and run the 43 mutations, then a fourth
review (`docs/STATUS.md` "Next cards" 0). The reviews also asked the architect panel for one rule
in design 8.5, "tenant code runs on real rows" (backlog 2026-11-10 S-21). Each review so far
found one more path, so one rule is better than more patches.

## The operations policy and the product direction (drafts for your approval)

- **Operations policy** (`docs/ops/policy.yaml`, `docs/ops/README.md`, 35 runbooks; design
  19.3). It lists every action type of the planned operations API in three classes: 28 green
  (an agent decides within limits), 16 amber (a second, independent agent agrees) and 16 red
  (you decide). Every action that is not listed is red. Rules can only raise a class. Aggregate
  limits stop an agent from splitting a large action into small ones. Every runbook has undo
  steps. The guard review found 9 blocking issues, for example cheaper paths around red actions
  and approvals that did not bind to what was approved. The revision applied every finding. **The
  revision itself had no second guard review.** Nothing is in force: there is no operations API
  before staging.
- **Product direction** (`docs/product/direction.md`; design 20.4). The vision ("your files,
  photos, databases and apps in one tree, with one permission system, built so that you and your
  AI agents can work in it safely"), target users, 10 things Ruum is not, 26 principles, and 8
  questions that the product manager agent scores ideas with. One open line depends on the AI
  gateway decision (design 17-37, backlog P-28).

## Risks

- **The build server is cut off.** The laptop's public IP changed, and the Hetzner firewall
  `ruum-buildbox` allows SSH only from the old address. Agents do not change a firewall. Until
  you change it, there is no smoke test, and mutation runs take hours on GitHub runners. The
  build server keys `q2` and `q2b` are still on the server.
- **Q-2 is the privacy core of step 2.** Agents cannot query databases on Postgres until it
  lands, and every review so far found a new raw-value path. Expect at least one more round.
- **P-3 and Q-2 conflict.** Whoever rebases Q-2 must keep both parts of `databases::build`.
  After Q-2, the masked copy must use the same column classes as the lens (backlog 2026-11-09
  S-18), or a copy can show a column in clear that the lens masks.
- **The operations policy** is long (1,567 lines of YAML) and has no schema or linter yet
  (backlog P-24). A second guard review should read the revision before you sign it.
- **The visual tests** miss small token changes (threshold 0.2, backlog T-22). A future theme
  change can pass CI while it looks different.
