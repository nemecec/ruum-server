# Digest run 14 (2026-11-21): step 3 wave 6 (runtime API, telemetry reads) and the app runtime on staging

Short report for the person (design 18.9). This run built the last two M2 code cards of step 3:
the runtime API binary with workload tokens (R-3) and the telemetry classes and reads (O-2). It
also built the staging half of the app runtime (I-6: gVisor nodes, the app gateway, the egress
proxy, the apps domain). All three are merged. Each panel decision is `provisional`; you can
veto any part. `main` is not pushed: the orchestrator pushes and deploys.

- **R-3: the runtime API.** A new binary, `ruum-runtime-api`, answers apps at `ruum.internal`
  (who am I, who holds a role, exchange a user token for a delegated token, read bound content
  and children, publish an event). It holds no tenant keys and no database credential: it asks
  the core over new internal routes (`/internal/runtime/v1/*`). The core issues workload tokens
  (EdDSA, 15 minutes, renewed) and takes the caller only from a verified token, never from the
  request body (review finding 1). The core also signs the delegated tokens, so the runtime API
  holds no private key. Tokens name their deployment, so the tokens of a replaced live
  deployment stop within 5 s (Kimi High); a trashed app stops at once. Caps per app, per tenant
  and per listener answer `429`; a slow body is cut after 10 s. Off without
  `RUUM_WORKLOAD_TOKEN_KEY_FILE`; no chart deploys the binary yet (I-4).
- **O-2: telemetry classes and reads.** Seven operations are built (search logs, metrics, one
  trace, the comparison of two deployments, the field listing, the confirmation of field
  classes, a pseudonym for a user), and the MCP server offers five read tools (82 tools in all).
  Field classes are stored in Postgres. An app's privacy file can only make a class stricter;
  only a person's confirmation relaxes it (two review findings). A pseudonym request stores no
  hash of the value (review finding 3). Reads have a budget, cursors are bound to the app and
  filter, and this app's spans are read first in a shared trace (Kimi Medium). The telemetry
  acceptance cases (15) pass on both backends. The journal now writes
  `app.telemetry_fields_confirmed`. No migration.
- **I-6: the app runtime on staging** (code and plan only; nothing applied). gVisor through a
  Talos system extension and a rolling `ops/upgrade-talos.sh`, the runtime class `gvisor`, the
  namespace `ruum-apps`, the gateway and the egress proxy in the `ruum` chart (images built,
  scanned and attested by `images.yml`), network policies, the edge site
  `*.*.apps.staging.ruumapps.net` with on-demand TLS, DNS records, smoke and netpol checks. The
  certificate `ask` endpoint now allows only hosts that can serve (a live app or a pending,
  running or ready preview by its short ID), so made-up names get no certificate (both
  reviews). `deploy-chart.sh` stops on a registry error instead of removing the running app
  runtime. Node22 apps still answer the gateway's 502 on staging: no runtime driver starts
  sandboxes on Kubernetes (I6-1).

No new external dependency (`ruum-runtime-api` is a new workspace crate that uses existing
workspace dependencies). No migration in this run.

## Risks

- **No card of this run has a Kimi APPROVE on its final code** (S-78). I-6 changes staging
  (Talos nodes, network policies, the edge) when the orchestrator applies it.
- **I-6 upgrades every staging node** to a new Talos installer (gVisor), one at a time, with a
  CNPG switchover each. The live release keeps serving, but a stopped upgrade leaves the nodes
  on two schematics; `upgrade-talos.sh --check` shows the state. Egress policy behaviour of
  kube-network-policies, Caddy's two-label wildcard on a real request and gVisor pods on cx23
  nodes are not verified yet (the netpol probe, `gvisor-check.sh` and `smoke-apps.sh` check them
  at the apply).
- `egress_deny_from` requires exactly `NODE_COUNT` nodes, so the platform step stops while a
  node is added or replaced (fail closed; P-117).
- O-2 writes the new journal type `app.telemetry_fields_confirmed`. Under design 12.7 (P-57) it
  may ship only after staging runs a release whose readers pass unknown types (`2303216` or
  later, on `main` since run 12).
- R-3's runtime routes on the core's internal listener refuse every call without the workload
  key (fail closed); the core's check of the user token at exchange is not there yet (R3-12).
- GitHub CI does not run four test binaries of the test kit (T-72); the build server's full
  runs do.
- Build server: a strict mutation shard's baseline failed once on a database provisioning wait
  while a full check ran (T-70); the data cluster drop under load (B-39, B-42) did not recur in
  this run.
